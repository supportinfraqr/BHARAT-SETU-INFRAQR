# BSS Audit Agent — runbook

Monthly audits only. The contractor runs them from the BSS portal after the
employer has approved the whole month's package. Reports and evidence are
retained for 7 years.

## 1. Architecture

```
BSS API (DB access)
  │ creates job folder + encrypted run.request
  ▼
/data/audit/jobs/<job_id>/
  ├── job.json
  ├── contractor_documents_<Month>_<Year>/
  │   ├── generated_clra_registers/
  │   └── uploaded_documents/
  ├── worker_documents/
  ├── bss_workers.json
  ├── run.request          (encrypted AI key — deleted after use)
  ├── status.json          (written by the runner)
  ├── output/
  └── logs/
  ▲
  │ shared volume only
  │
audit-runner container (NO DB, NO BSS network)
  • reads run.request, decrypts the key in memory
  • runs run_agent.py
  • writes status.json
  • outbound HTTPS only
```

A BSS-side cron (`sync_audit_jobs`) reads `status.json` and updates `AuditJob`.

## 2. What the agent compares

For the selected contractor + site + previous month:

- the workers in the submitted registers/forms
- against the workers bound to that contractor at that site in that month
- using name, father name, DOB, Aadhaar, PAN, UAN, ESIC, bank account, DOJ,
  designation and site
- plus the worker's Aadhaar/PAN/bank/appointment/photo documents

Workers who were at the site in September but left in October are still included
for September. The BSS side builds `bss_workers.json` from the historical
binding, and the agent overlays it on the worker-document ground truth.

## 3. Approval and run rules

- Employer approval is **whole package only** (Approve all / Reject).
- Only VERIFIED current batches and evidence are included.
- Monthly only; no quarterly/half-yearly/yearly.
- Any previous month; no current/future month.
- **Two runs per contractor/site/month** by default; BSS Admin can change the
  limit per pair.
- **Only the contractor can run**; the employer views reports; BSS Admin
  configures limits.
- A second run creates a new version; both are retained, latest marked current.

## 4. Job folder contract

`job.json` accepts only:

```json
{
  "principal_employer": "...",
  "contractor_legal_name": "...",
  "site": "...",
  "site_short": "...",
  "state": "MH",
  "state_name": "Maharashtra",
  "wage_month": "2026-09",
  "headcount_establishment": 123,
  "nature_of_work": "...",
  "is_construction": false
}
```

`bss_workers.json` is generated by BSS. Do not edit it by hand.

## 5. Run the agent manually (for debugging)

On a host with the agent extracted:

```bash
export DEEPSEEK_API_KEY='sk-...'
export DEEPSEEK_BASE_URL='https://api.deepseek.com'
export DEEPSEEK_MODEL='deepseek-chat'
export DEEPSEEK_CACHE_DIR='/tmp/bss-audit-cache'

python run_agent.py \
  --groundtruth /data/audit/jobs/<job_id>/worker_documents \
  --query /data/audit/jobs/<job_id>/contractor_documents_September_2026 \
  --job /data/audit/jobs/<job_id>/job.json \
  --out /data/audit/jobs/<job_id>/output
```

This is for debugging only. Production uses the isolated runner.

## 6. Run the production runner

The runner image is built from `Backend/audit_agent` + `Backend/audit_runner`.
It has no Django/DB code.

```bash
cd ~/bss/FINAL/deploy-prod
sudo docker compose up -d --build audit-runner
sudo docker compose logs -f audit-runner
```

Environment (both backend and runner):

- `BSS_AUDIT_HANDOFF_KEY` — shared secret used to encrypt the active AI key
- `BSS_AUDIT_JOBS_DIR=/data/audit/jobs`
- `BSS_AUDIT_AGENT_DIR=/app/audit_agent` (runner)
- `DEEPSEEK_CACHE_DIR=/data/audit/cache` (runner)

Generate the handoff key once and put it in `deploy-prod/.env` and
`deploy-staging/.env`:

```bash
openssl rand -hex 32
```

The runner must be attached only to `audit_net`. It has no DB credentials and no
route to the DB/backend.

## 7. Sync status into the DB

The API only writes `run.request`; it does not run the agent. A BSS-side cron
must run:

```bash
BSS_MODE=prod bash ~/bss_scripts/sync_audit_jobs.sh
```

Install every minute (idempotent):

```bash
crontab -l 2>/dev/null | grep -v sync_audit_jobs | crontab -
(crontab -l 2>/dev/null; echo '* * * * * BSS_MODE=prod bash ~/bss_scripts/sync_audit_jobs.sh >> ~/bss_audit_sync.log 2>&1') | crontab -
```

`sync_audit_jobs` reads `status.json` and updates the job's status, report paths,
summary and token usage. It deletes the request after READY/FAILED.

## 8. Active AI provider

BSS Admin → AI Audit Settings must have an **enabled default DeepSeek** credential.
The BSS backend encrypts its key into `run.request`; the runner decrypts it in
memory. The key is never written to `job.json`, reports, evidence or logs.

If the active provider is not DeepSeek, the contractor gets a clear error and no
job is queued.

## 9. Replication steps

1. Verify the original tarball checksum and keep it in a private archive.
2. Copy only `bss_agent/`, `config/`, `assets/`, the catalogue, `run_agent.py`
   and requirements into the runner image.
3. Install `poppler-utils` and the runner requirements.
4. Create `BSS_AUDIT_HANDOFF_KEY`.
5. Build the `audit-runner` image and create the `audit_net` network.
6. Mount only `audit_data:/data/audit`.
7. Start the runner; confirm it has no DB env and only `audit_net`.
8. Add the same handoff key to the backend/worker environment.
9. Configure the BSS Admin active DeepSeek credential.
10. Install the `sync_audit_jobs` cron.
11. Run one offline sample test, then one real monthly job.

## 10. Troubleshooting

| Symptom | Check |
|---|---|
| Job stays PENDING | Is `audit-runner` running? Is `run.request` present? |
| `No active AI provider` | BSS Admin → AI Audit Settings: enabled/default DeepSeek credential |
| `active provider must be DeepSeek` | Change the BSS Admin default provider |
| Runner says missing `pdftotext` | Install `poppler-utils` in the runner image |
| Job FAILED with 401/402 | DeepSeek key invalid or out of balance |
| No worker documents | The binding period/historical worker query may be empty |
| Package not approved | Employer must Approve all for that contractor/month |
| Run limit reached | BSS Admin can change `runsPerMonth` for the contractor/site |

## 11. Security

- Runner: no DB env, no BSS backend network, no DB route, read-only root
  filesystem, dropped capabilities, no-new-privileges, resource limits.
- Handoff key: shared only by backend/worker and runner.
- AI key: encrypted at rest in `run.request`; decrypted in memory; request
  deleted after use; never logged.
- Job folders: private, mode 0700; reports served only through authenticated BSS
  endpoints; retained 7 years.
- Original tarball (with sample PII) is **not** committed to Git.

## 12. Legacy report pipeline retired

The monthly Document Audit Agent and its isolated runner are now the only audit
report pipeline. Removed from the product:

- the global compliance AI audit (workspace + endpoints + UI)
- the quarterly audit engine/export and admin generation option
- the per-submission AI report endpoints and "AI report"/PDF actions
- the old contractor "Detailed AI Report" actions

Historical `ComplianceReport`/`AuditReport` rows and stored files remain in the
database for retention; no new reports are generated by the old code.
