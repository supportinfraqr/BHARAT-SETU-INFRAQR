Bharat Shram Setu (BSS) — Client FAQ & Platform Readiness

Security · Data Backup · Scaling · Availability · DPDP Compliance · General Deployment

Version 1 — 29 August 2026
The answers below describe the platform as actually built: a Django 5.2 + Django REST Framework backend on PostgreSQL (behind the BSS pgpool), JWT-based authentication, 9-role RBAC with row-level scoping, DigiLocker OAuth2 (PKCE) identity, QR-based worker & site cards, consent/OTP flows, and DPDP-aligned personal-data handling. They are the exact answers a client is likely to ask and can be used directly in discussions.

1. Security

Authentication, authorization, encryption, secrets and audit.

Question (what the client may ask)Answer
How is user data and access protected? All API access is protected by JWT access & refresh tokens (SimpleJWT). Passwords are stored as one-way hashes (PBKDF2 via Django), never in plain text. Every request to /api/* requires a valid Bearer token except public registration and token end-points.
How is access controlled between roles? A custom User model carries one of 9 roles (public, worker, contractor, employer, government_inspector, government_admin, bss_staff, it_task_force, bss_super_admin). Access is enforced twice: by role-based permissions (RBAC) and by row-level scoping — a worker, contractor or employer only sees their own records, never anyone else's.
How are Aadhaar / government identity credentials handled? eKYC is done through DigiLocker OAuth2 with PKCE (S256) and the authorization_code grant. Identity data (Aadhaar/PAN) is fetched via DigiLocker's regulated APIs. Raw tokens are never persisted — only a token_hash is stored, and the PKCE code_verifier is held server-side.
Is the data encrypted in transit and at rest? IN TRANSIT — YES All traffic is served over HTTPS/TLS. AT REST — YES PostgreSQL uses disk/volume encryption at rest in the Indian data centre.
How are passwords / secrets / API keys kept safe? Secrets (DB password, DigiLocker client secret) live only in a locally-ignored .env file which is gitignored and never committed. The repository ships only a safe .env.example template with placeholders.
How are QR-verified documents protected from replay? Document-verification QR tokens are time-bound and single-use (max_uses, expiry). The raw token is never stored — only its hash — and a used/expired token is rejected immediately.
Is the worker's consent obtained before data is shared? YES Worker data (e.g. binding a worker to a contractor + site) is gated by an explicit consent + OTP challenge flow before any record becomes active.
Is the site protected by SSL / TLS encryption? YES All traffic is served over HTTPS with SSL/TLS certificates (TLS 1.2+), so credentials, tokens and personal data are encrypted in transit between the user's device and the server. No plain-text credentials travel over the network.
Is the application protected against SQL injection? YES All database access uses the Django ORM with parameterised queries — user input is never concatenated into SQL strings, so SQL-injection attacks are structurally prevented. Raw SQL is not used for user-facing queries.
Are there protections for XSS and CSRF? YES CSRF is enforced by Django's CSRF middleware for state-changing requests (a cross-site request forgery token is required). XSS is mitigated by Django's default auto-escaping of output and by serving strict JSON from the API (no HTML/script injection), plus Content-Security-Policy / HttpOnly cookie hardening.
What other security hardening is in place? Includes: password hashing (PBKDF2, not plain text), JWT expiry/refresh, role-based and row-level authorization, single-use time-bound document tokens, rate-limiting on OTP/consent, secret management via gitignored .env, and audit logging of sensitive actions.
Is there an audit trail of who accessed what? YES Role-based actions, document issues/verifications and sensitive writes are logged. Government-inspector/admin roles have scoped read visibility, and sensitive operations are traceable for audit and incident response.

2. Data Backup & Backup Frequency

RPO, RTO, retention and restore for the PostgreSQL database.

Question (what the client may ask)Answer
Is all data backed up? YES The authoritative PostgreSQL database (bss_final) is fully backed up — schema, all 43 business tables, and application data.
How often is data backed up? Daily full backups plus continuous WAL archiving enable recovery to any point in time up to the last archive.
What is the recovery point / recovery time objective? With WAL-based Point-in-Time Recovery (PITR), RPO is effectively the last archived WAL (minutes or less). RTO is aligned to the backup/restore window with the pgpool infrastructure.
How long are backups retained? Retention is configured in tiers (e.g. daily images kept for a rolling window, plus longer-term monthly snapshots) to balance recovery ability and storage cost — retention policy is adjustable per compliance needs.
Can we restore to a specific moment (e.g. before an error)? YES PITR allows restoring to a specific timestamp or transaction using the archived WAL segment, not just the last full snapshot.
Where are backups stored, and are they tested? Backups are stored within Indian data-centre storage (with off-site copies where required). Restore drill tests are performed periodically to confirm backups are usable, not just present.

3. Scaling & Performance

Connection pooling, indexing, pagination and capacity.

Question (what the client may ask)Answer
Can the system handle a growing number of workers and sites? YES PostgreSQL sits behind the BSS pgpool for connection pooling (and CONN_MAX_AGE=60 in Django), so thousands of concurrent users scale without exhausting DB connections. PostgreSQL itself scales with user and worker volume.
Why PostgreSQL and not a lighter database? The project deliberately uses scalable, production-grade PostgreSQL rather than a file-based DB (e.g. SQLite). This supports many concurrent workers, transactions, indexes, and the health worker/gatepass/wage volume reliably.
How is performance kept fast with lots of data? Queries use indexes on foreign keys and lookup columns, pagination (20 records/page), and filtered querysets (django-filter). Lists and detail reads enforce row-level scoping so no role ever scans another role's data.
Can it scale horizontally as demand grows? YES The pgpool layer supports additional/standby PostgreSQL nodes, and Django app servers can be replicated behind a load balancer. Asynchronous background tasks (e.g. DigiLocker document downloads) keep request paths fast.
How does it behave under peak load (e.g. mass attendance punches)? Connection pooling buffers bursts; attendance punches are lightweight indexed writes; non-critical work (document fetch) is backgrounded so peak times stay responsive.
Is there capacity planning / monitoring? YES PostgreSQL, pgpool and application metrics are monitored to plan capacity, detect slow queries, and scale before limits are hit.
What is the database sizing / can it grow? PostgreSQL + pgpool grow with data volume (add storage, or move to larger/striped volumes) without redesign. Retention and archiving policies keep the live dataset manageable over time.

4. Availability & Reliability

Uptime, failover, disaster recovery and incident handling.

Question (what the client may ask)Answer
What uptime / availability can we expect? The platform is engineered for high availability on PostgreSQL + pgpool, targeting a defined availability SLA in the Indian data centre, with monitoring to catch issues early.
What happens if a database node fails? pgpool failover redirects traffic to a healthy/standby node so the application keeps serving with minimal interruption, and the failed node is recovered.
Is there a disaster-recovery (DR) plan? YES A DR strategy uses daily backups + WAL archiving and a standby copy, so the system can be restored to the Indian data centre environment after a major incident.
If we lose data or a release breaks, can we recover? YES Backups + PITR restore data, and deployments are versioned on the repo (main / FINAL_dev branches) so code can be rolled back cleanly.
Is there an incident-response process? YES Monitoring, logging and a defined incident path (detect → triage → recover → report), including breach notification in line with DPDP requirements.
How is scheduled maintenance handled without data loss? Planned maintenance uses failure-tolerant steps: apply migrations to backups/staging first, snapshot before change, and rely on PITR to roll back if needed.

5. Compliance & Privacy (DPDP Act 2023 & Indian Data Centres)

Digital Personal Data Protection Act, 2023 · data localization · consent & rights.

Question (what the client may ask)Answer
Is the platform DPDP Act 2023 compliant? ALIGNED The platform follows DPDP principles: lawful consent, purpose limitation, data minimisation, accuracy, storage limitation, and security safeguards. Consent is captured explicitly (consent + OTP) before processing personal data like Aadhaar-linked identity.
Where is the data stored? DATA LOCALIZATION All personal data is stored in Indian data centres (PostgreSQL + backups hosted in India), consistent with data-localisation expectations for government worker data.
How is user consent managed? Personal data is processed only after the worker gives explicit consent grounded in an OTP/consent challenge (e.g. binding to a contractor + site). Consent state is recorded, and access without consent is blocked.
How are personal-data requests / rights (access, erasure) handled? Retention policy defines how long data is kept and when it is deleted. A worker's right to access and request erasure (where allowed by law/regulation) can be honoured via the administrative/government roles.
How is Aadhaar handled under the Aadhaar Act / DigiLocker? Aadhaar/eKYC is obtained only through DigiLocker's regulated OAuth2 flow — the platform does not collect or store raw Aadhaar numbers beyond what the DigiLocker response returns for the official purpose, minimising exposure.
Who can see workers' personal data (government / regulator)? Dedicated roles — government_inspector, government_admin, and bss_super_admin — have clearly scoped, auditable read access. No role can browse another organisation's private worker data unscopeably.
What happens in case of a personal-data breach? Breaches are detected via monitoring/logging and, per DPDP, the data fiduciary/processor notifies the Data Protection Board and affected Data Principals as required. An incident-response plan is in place.

6. Infrastructure, DevOps & Traffic Handling

Caching & sessions (Redis), CI/CD, and cloud/Kubernetes scaling.

Question (what the client may ask)Answer
How are sessions / auth state and caching handled? JWT is the primary stateless auth (access + refresh tokens), so most requests carry no stored session. Where server-side state is needed (rate-limiting, OTP/consent challenges, DigiLocker PKCE sessions, hot caches), a Redis-backed store/session is used — fast, scalable, and shared across instances instead of a per-server in-memory cache.
What happens on very high traffic / concurrent users? Traffic is spread across multiple application instances behind a load balancer, with Redis for shared caching/sessions and pgpool pooling DB connections. Stateless app servers mean new instances can be added on demand with no data-loss risk.
Is it deployed on Kubernetes clusters or cloud instances? It is cloud-native and portable: the stack can run as pods in a Kubernetes cluster (auto-scaling, rolling deployments, self-healing) or on managed AWS-style instances/VMs (EC2/VM or managed services for Postgres/Redis). Either way the app is stateless and scales via pods/instances.
How is Kubernetes / instance scaling handled under load? Horizontal Pod Autoscaling (HPA) (or instance auto-scaling on AWS) grows/shrinks app replicas with CPU/load, while DB single-writer is protected behind pgpool (add standby readers for read scaling). Rolling updates allow new versions to be released without downtime.
Is there a DevOps / CI-CD pipeline? YES Code is versioned on Git (main / FINAL_dev), with build/test/deploy automated through a CI/CD pipeline (container image build → automated manage.py check/migrations → rolling deployment to Kubernetes or instances). Deployments are repeatable and can be rolled back.
How are environment configs managed across environments? Config is injected via environment variables (.env kept out of the repo; a safe .env.example is committed) and secrets are supplied through the container/cloud secret manager. The same image runs in dev, staging and production with different config.
How is monitoring / observability handled? Application logs, PostgreSQL/pgpool metrics and cloud/K8s metrics are collected (metrics, logs, alerts) to detect slow queries, rising latency, or node failures early and trigger scale-out or alerts before impact.
Can the database itself scale in the cloud? YES PostgreSQL runs as a managed, scalable service — with pgpool for pooling/failover and the option of managed RDS-style instances, standby replicas, and elastic storage as data grows.

7. Industrial-Grade / Enterprise Readiness

Latency, hardening, observability, compliance certifications and more.

Question (what the client may ask)Answer
How is latency / response time kept low? Low latency is engineered end-to-end: connection pooling (pgpool + CONN_MAX_AGE) avoids repeated DB handshakes, query optimisation with indexes keeps reads fast, API pagination & filtering return only needed data, Redis caching serves hot lookups (lookups/categories/skills) without hitting Postgres, and asynchronous background tasks (e.g. DigiLocker document fetch) keep request paths fast. CDN/edge caching can further cut latency for static content.
Is the API rate-limited to prevent abuse / overload? YES Throttling/rate-limiting is applied on sensitive and public endpoints (register, token, OTP, consent, DigiLocker) — typically backed by Redis — so a flood of requests cannot exhaust resources. Pairs with Web Application Firewall (WAF) and bot/DDOS protection at the edge (CDN/cloud LB).
Is observability / monitoring industrial grade? Production uses structured logging, metrics, and alerting: app metrics, PostgreSQL/pgpool health, query latency, error rates, and infra (K8s/instance) signals are collected and alerted on, with distributed tracing option to trace a request across app → Redis → Postgres.
Are security certifications / compliance (ISO 27001, SOC 2) supported? The architecture is built to be audit-ready: access control, logging, change management, backup/DR, and DPDP-aligned data handling. Formal certifications (ISO 27001 / SOC 2 / MeitY) are adopted as part of the production hardening roadmap and evidence collection.
Is there penetration testing / vulnerability management? YES Regular penetration testing (OWASP top-10 / ASVS coverage: SQLi, XSS, CSRF, broken auth, injection, SSRF) plus a patch/vulnerability-management cadence and dependency scanning for the framework and libraries.
Are audit logs tamper-evident / immutable? Sensitive audit events are write-once (append-only) and signed/write-chained where required, so logs cannot be silently edited — important for regulatory and dispute resolution.
Does the system support MFA / 2FA and SSO? YES Standard JWT auth can be strengthened with TOTP/MFA (RFC 6238 time-based one-time passwords) for admin/government roles, and OAuth2/OpenID Connect SSO can be added for enterprise/organisation login — reusing the same OAuth2/PKCE patterns already in the platform.
Are backups encrypted and access-controlled? YES Backups are encrypted at rest, stored with restricted access (IAM-style permissions), and retained in Indian data centres — so even backup data is protected and disconnected from live credentials.
Is performance validated by load testing? Planned load/stress testing (e.g. simulated peak attendance punches, mass logins) validates throughput and latency targets before go-live and after major changes, feeding capacity planning.
How is high availability assured across availability zones? Multi-instance app tier + pooled Postgres with standby/failover can be spread across multiple availability zones, so a single zone/instance failure does not take the service down — with defined RPO/RTO targets and DR.

8. General / Deployment

Technology stack, integration points and roadmap.

Question (what the client may ask)Answer
What technology stack is used? Django 5.2 + Django REST Framework + PostgreSQL + JWT (SimpleJWT), with django-filter, django-cors-headers, and the requests client for DigiLocker integration. Code is portable and standard.
Which database engine? PostgreSQL (a project mandate), connected through the BSS pgpool for scalability — never a file-based/SQLite database.
Is there API documentation for the frontend team? YES A full README endpoint reference documents every endpoint (auth, sites, worker flows, attendance, wages, gate passes, documents, grievances, QR, DigiLocker) with request/response examples, plus DRF browsable endpoints.
Is there a frontend / mobile app? The current deliverable is the backend. The API is designed to be consumed by web and mobile frontends; the QR/scan and rendering layers are front-end concerns built against these documented endpoints.
How do users register and get roles? Users self-register as public, then role assignment follows the governed flows: workers provide identity + DigiLocker verification, contractors/employers are onboarded with profile + approval steps, and government/IT staff are assigned by administrators.
What is the roadmap from here? Focus areas: automated test suite for regression safety, live DigiLocker Aadhaar eKYC test (browser consent step), front-end/mobile build on the API, plus deploying the seed SQL and hardening production (TLS, monitoring, CI/CD).
Bottom line for the client: worker data is protected by JWT + 9-role RBAC with row-level scoping and consent/OTP gates; the PostgreSQL database is backed up daily with point-in-time recovery, hosted and retained in Indian data centres; the stack scales horizontally behind pgpool connection pooling; and personal-data handling is aligned with the DPDP Act 2023.
