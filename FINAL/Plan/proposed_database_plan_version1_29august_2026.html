Bharat Shram Setu — Unified Authentication & Database Design Reference

Source: BSS_Final_worker_form_and_permission.xlsx
This document defines the system roles used across the Bharat Shram Setu platform and how they are represented in the single unified authentication table. Every user is identified by one role value and an account_active status. On the Secure Authentication screen, the user is asked to Select Role from the login roles below.

Document Overview

  1. Base Roles — the role definitions and the role enum.
  2. Auth Support — signup / login options, authentication methods, and how each role authenticates.
  3. Tabular Structure — the database tables that store users, credentials, and account state.

Signup Options

A user can register using multiple identification (signup) modes. Credentials are stored variationally in the user_credentials child table rather than as fixed email/mobile columns on the user, so a single account can register and later sign in with more than one mode.

Signup Option Type Description

Phone mobile Credential Register with a mobile number
Aadhaar Login aadhaar Credential / Single Sign-On Register / sign in using Aadhaar-based authentication (OTP / secure)
Login ID login_id Credential Internal platform ID used by BSS Staff / IT Task Force

Login Authentication Methods

For login, the platform allows the following authentication (verification) methods. These are the ways a user proves their identity when signing in, independent of which identifier they use.

Method Type Description
Phone Number Login Phone Number Login using the mobile number as the identifier, with OTP verification sent via SMS, WhatsApp, or phone call.
Email + Password Email & Password Login using an email identifier along with a stored hashed password.
Email + MPIN Email & MPIN Login using an email identifier along with a numeric MPIN (mobile PIN).
ID + MPIN Login ID & MPIN Login using a login ID (internal platform ID) along with a numeric MPIN.
ID + Password Login ID & Password Login using a login ID (internal platform ID) along with a stored hashed password.
All methods may be enforced with additional security (MFA) as configured by the Super Admin.

User Management — Super Admin

There is a single Super Admin role. Other privileged roles — IT Task Force, Government (Inspector and Admin), and BSS Staff — are separate roles, each with their own users. The Super Admin has full control over users and accounts.

Capability Description
Create any user Create a user with any role (Worker, Contractor, Employer, Government Inspector, Government Admin, BSS Staff, IT Task Force)
Assign role Assign or change a user's role at creation or later
Activate account Activate a user's account so they can sign in
Deactivate account Deactivate any user's account to block sign-in
Manage credentials Set up / reset the user's signup identifiers (mobile / email / aadhaar / login_id)
Account activation is controlled by the account_active flag on the users table. A deactivated account cannot sign in regardless of role.

user_credentials (login / identification)

Stores one row per identification mode a user has signed up with. A user can have multiple credentials (mobile, email, aadhaar, login_id) and can sign in using any of the supported authentication methods.

Column Type Description

identity_value VARCHAR The identifier value (mobile number, email, Aadhaar, login ID)
is_primary BOOLEAN Whether this is the primary identifier (e.g., Aadhaar primary for Worker)

Role-Specific Tabular Structure

Only the Worker profile is fully defined at present, based on the Worker form & Access sheet of the source workbook. It is linked back to the unified users table via user_id (role = 'worker') and is organised into 10 resource tables (one per section of the form). Worker data is pure data — no permission columns live on these tables. Every field-level access rule lives in the single RBAC permissions table.

Alongside the worker resources sit the role profile tables (contractor_profiles, employer_profiles, government_profile, bss_staff_profile, it_profile), the site table, and the worker_contractor_binding link. Contractor / employer / site details are not stored inline on the worker employment row — they are referenced via worker_employment.assignment_id → worker_contractor_binding, and the worker’s employer is derived through the site (site.employer_id). These relations follow the E–C–S–W binding constraints (1 worker = 1 site; one contractor may bind to many employers through many sites).

Permission seed (1,660 rows): FINAL/Db/seed_rbac.sql; QR access profile seed: FINAL/Db/seed_qr.sql; reference / dropdown seed: FINAL/Db/seed_lookup.sql; worker-category master seed: FINAL/Db/seed_worker_category.sql; skill master seed: FINAL/Db/seed_skill_master.sql; document master seed: FINAL/Db/seed_document_master.sql (all regenerate with generate_seed_rbac.py).

System Logic, Entity Relationships & Consent Fallbacks

The following rules and logical flows are compiled from the core system requirements to ensure database consistency, correct field-level data exposure, and seamless communication fallback handling during worker/contractor/site binding.

2. QR-Based Consent & Communication Managers

All scans require a dual-handshake consent process. When network or hardware limitations prevent immediate confirmation, the system triggers targeted fallbacks.

Flow CaseTrigger ScenarioPrimary ActionFallback Mechanism
Case I (Top-Down)
E → C → W		 Contractor scans worker's physical card; worker may not have a smartphone. Push notification sent to Worker app (60-second window). IVR Phone Call: If no response, system dials the worker's registered phone, offering keypad prompts (Press 1 to accept, Press 0 to decline).
Case II (Bottom-Up)
W → C → E		 Worker scans Contractor QR; app-to-app communication is delayed by network connectivity. Push notification sent to Contractor/Employer app. SMS OTP & Voice Call: If app response times out (60s), system sends an SMS OTP. If OTP entry fails or times out, it triggers a voice call fallback.

3-Stage Consent Escalation — Non-Smartphone (Feature-Phone) Users

The client requires that workers without a smartphone are still able to give verified, explicit consent. The consent channel follows a 3-stage escalation ladder. The two fallback methods are:

  • OTP (worker gives the code to the contractor): the worker receives a one-time code by SMS on their phone and tells/gives the OTP to the contractor, who types it into the contractor's app. Once verified, consent is granted.
  • IVR works like 1 / 0: an automated call to the worker with "Press 1 to accept, Press 0 to decline". The worker's keypad digit (1 or 0) is the consent decision — no code needs to be typed.
StageChannelHow consent is givenTimeout
1st APP push Worker acknowledges the consent in the BSS mobile app (only applicable when the worker has a smartphone/app). 60 s
2nd IVR (1 / 0) Automated call to the worker's registered phone: "Press 1 to accept, Press 0 to decline". The worker's keypad press (1 = accept, 0 = decline) is the consent decision — no code entry. 60 s
3rd OTP SMS OTP: the system sends a one-time code to the worker's phone. The worker gives/reads the OTP to the contractor, who enters it on the contractor's app. On successful verification, consent is granted. OTP valid 5 min
For a worker with no smartphone, stage 1 (APP) is skipped. Consent is obtained via IVR (stage 2, Press 1/0) and, if needed, OTP (stage 3) — where the worker reads the SMS OTP to the contractor and the contractor enters it in the app. This applies to bind, unbind and the grievance consent flows.

Site-Based QR Codes & Site-Linked Worker Binding

The employer is allowed to generate site-based QR codes. When the employer binds a contractor, the employer also marks/associates the site for that binding. A worker can then be attached to that site by the contractor. This gives a concrete assembly line: Employer → Site → Contractor → Worker.

  1. Employer creates site-based QR codes. The employer registers one or more sites and generates a unique QR code per site (site_qr_token), scoping attendance/consent/binding to that physical location.
  2. Employer binds contractor and marks the site. During the EMPLOYER_CONTRACTOR binding, the employer selects the site. This is recorded on the binding via binding_scope / site linkage, so the contractor is bound to a specific site (UNIQUE(worker_id, contractor_id, site_id) tuple with site as part of the constant E-C-S-W identity).
  3. Contractor attaches the worker to the site. With the employer-contractor binding (and site) in place, the contractor binds the worker against that same site. The resulting WORKER_CONTRACTOR binding inherits the site from the employer-contractor binding, so the worker is attached to the site through the contractor.
StepActorActionResult / Stored record
1Employer Registers a site and generates a site-based QR code (site_qr_token). A site record with its own QR identity for scanning.
2Employer Creates EMPLOYER_CONTRACTOR binding and marks the site. Binding scoped to the site; contractor is associated with employer + site.
3Contractor Binds the worker (WORKER_CONTRACTOR) against the same site. Worker attached to the site via the contractor; constant E-C-S-W tuple fulfilled.
The site is part of the binding identity (UNIQUE(worker_id, contractor_id, site_id)). A worker can be attached to a site only after the employer has bound the contractor to that site. Scanning the site QR provides site context for attendance, consent and profile visibility.

A provisional worker_gate_pass table (TGP/PGP child table with start/end date, status, issued_by, source) already exists in the schema, but it is pending client confirmation on the questions above and may change.

3. Data Visibility Interception

Rule 5 & 6 (Interception Rule): Before rendering profile details, the system checks for an active binding. If bound, 100% of the database view is exposed to the contractor/employer. If unbound, the view is strictly restricted to general details: Name, Age, Sex, Company, and Blood Group.

C. Database Scaling Strategy (1 crore users)

StrategyApproach
Connection poolingRDS Proxy in front of PostgreSQL so thousands of Django connections collapse into a bounded pool.
Read replicasRead-only replicas absorb the read-heavy profile/QR/listing queries; primary handles writes.
IndexingComposite indexes on join paths (role, site, worker_contractor_binding), user_credentials(identity_type+value), unique tuple constraints (E-C-S-W).
Hot-path cachingQR scan / profile view results cached in Redis with short TTL + invalidation on write, cutting DB reads by ~80–90%.
Table partitioningPartition high-growth tables by range (rozgar_request by month, worker_documents by year, audit logs) for fast pruning.
ArchivalArchive/expire old grievance, request, and scan-log rows to S3/Glacier via lifecycle; keep DB hot set small.
Duty separationAnalytical/reporting queries run on dedicated replicas or OpenSearch, never against the transactional primary.
CapacityStart with Multi-AZ r6i.xlarge + 2 read replicas; scale up/out with load; use Aurora PostgreSQL for even larger auto-scaling read replicas if needed.
