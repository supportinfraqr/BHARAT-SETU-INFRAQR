Detailed IT Architecture Discovery — Technical Questions with Examples & Scale-Up Proposal
Important context: AWS is already known to be the hosting environment, and the current BSS platform does not currently have a QR solution. The discovery should therefore focus on the existing frontend/backend, APIs, data model, deployment and operational controls, so that our QR + identity binding + geolocation + attendance solution can be integrated with the existing platform.

Meeting objective: Understand the existing BSS architecture first, without assuming that any particular technology is required. Each question below is accompanied by a concrete e.g. example to clarify the expected answer. The answers should then be used to design a target architecture for higher availability, security, observability and scale, with a future path toward approximately 1 crore (10 million) identities and high-volume QR/attendance transactions.

1. CI/CD & Secure Software Delivery

Understanding the build-and-release pipeline, automation level, and rollback safety.
What is your current CI/CD pipeline?
e.g., GitHub Actions, GitLab CI/CD, Jenkins, Azure DevOps, Bitbucket Pipelines, ArgoCD
What is it?
CI (Continuous Integration) automatically builds and tests code changes as developers merge. CD (Continuous Delivery/Deployment) automates delivery to staging or production.
Why we ask:
A mature pipeline makes releases repeatable, auditable and less dependent on manual server operations.
Are builds, unit tests, and integration tests automated?
e.g., Jest, Mocha, Cypress, Playwright, Selenium, JUnit, PyTest, SonarQube
What is it?
Automated tests validate code behavior consistently on every commit/PR without manual intervention.
Why we ask:
Higher release frequency and larger systems require automated regression protection.
Do you perform security scanning — SAST, dependency, or container scanning?
e.g., SonarQube, Snyk, Trivy, Checkmarx, GitHub CodeQL, Dependabot, AWS ECR scanning
What is it?
SAST analyzes source code for security flaws. Dependency scanning checks third-party libraries for known CVEs. Container scanning checks Docker images for vulnerabilities.
Why we ask:
Detects security weaknesses early in the pipeline before they reach production.
What is your rollback strategy if a deployment fails?
e.g., Redeploy previous Docker image tag, EC2 AMI snapshot restore, Git revert + rebuild, ECS task definition rollback, ALB target group switchback
What is it?
A rollback mechanism reverts the application to the last known-good version when a new deployment introduces issues.
Why we ask:
Fast rollback minimizes downtime and prevents bad code from affecting users.
Can you deploy without downtime — zero-downtime or blue-green deployments?
e.g., Blue-green via ALB, ECS rolling update, Kubernetes rolling update, canary deployments, feature flags (LaunchDarkly)
What is it?
Zero-downtime deployment replaces application instances without dropping active user connections. Blue-green runs two identical environments and switches traffic.
Why we ask:
Critical for worker attendance systems that must remain available during updates.

What is your compute/containerization approach — VMs, Docker, Docker Compose, ECS, or Kubernetes?
e.g., EC2 VMs, Docker Compose, AWS ECS Fargate, AWS EKS, self-managed Kubernetes, bare EC2 + PM2/systemd
What is it?
VMs are virtual servers. Docker packages applications into portable containers. Kubernetes orchestrates many containers across hosts with auto-scaling and self-healing.
Why we ask:
Tells us how portable and independently scalable the current application is. Kubernetes is useful when operational complexity justifies it.
What technology/framework is the existing frontend built on?
e.g., React 18 + TypeScript, Angular 16, Vue 3 + Vite, Flutter, React Native, native Kotlin (Android), Swift (iOS)
What is it?
Frontend frameworks determine the application's UI architecture, state management, and build toolchain.
Why we ask:
Determines how our QR, geolocation, and attendance capabilities can technically integrate with the existing application.
Is the application running on a single instance or multiple instances? Do you have auto-scaling?
e.g., AWS Auto Scaling Group, ECS Service Auto Scaling, Kubernetes HPA, AWS Application Load Balancer, Nginx reverse proxy
What is it?
Multiple instances allow traffic distribution and failover. Auto-scaling adds/removes instances based on traffic or resource utilization.
Why we ask:
A single instance is a bottleneck and single point of failure. Horizontal scaling is needed for high-volume QR scans and attendance.
Do you have separate Development, UAT/Staging, and Production environments?

What is it?
Development is where engineers build. UAT (User Acceptance Testing) is for business validation. Production is the live system.
Why we ask:
Separating environments prevents development changes from directly impacting real users and production data.

3. API Architecture & Security

How backend APIs are exposed, authenticated, versioned, and protected from abuse.
How are BSS APIs currently exposed and secured?
e.g., REST APIs, GraphQL, gRPC, WebSockets, HTTPS + TLS 1.2+, JWT Bearer tokens, API keys, OAuth 2.0
What is it?
APIs (Application Programming Interfaces) allow the frontend to communicate with backend services. They must be encrypted (HTTPS/TLS) and authenticated.
Why we ask:
Identifies the integration mechanism our new QR, identity, and attendance services should use.
Do you use an API Gateway for routing, authentication, and rate limiting?
e.g., AWS API Gateway, Kong, Nginx reverse proxy, Traefik, Envoy, Apigee, Tyk
What is it?
An API Gateway is a single entry point that handles routing, authentication, rate limiting, request/response transformation, and logging for all APIs.
Why we ask:
If one already exists, it becomes the natural integration boundary for our new services.
How are APIs authenticated?
e.g., JWT (HS256/RS256), OAuth 2.0 + OIDC, AWS Cognito, Auth0, session cookies, API keys, mTLS
What is it?
JWT is a signed token for stateless API auth. OAuth 2.0 is an authorization framework for delegated access. OIDC adds identity on top of OAuth 2.0.
Why we ask:
Our services must integrate securely with the existing authentication mechanism rather than creating conflicting sessions.
Do you have rate limiting on sensitive endpoints like attendance and QR validation?
e.g., API Gateway throttling, Nginx rate limiting (limit_req), Redis-based rate limiter, token bucket, leaky bucket algorithms
What is it?
Rate limiting restricts how many requests a client can make in a given time window, preventing abuse and protecting backend resources.
Why we ask:
Without rate limiting, a spike in QR scans or attendance submissions could overwhelm the backend or database.
How do you handle API versioning and backward compatibility?
e.g., URL-based: /api/v1/, /api/v2/; Header-based: Accept-Version; Query parameter; OpenAPI/Swagger spec
What is it?
API versioning allows multiple versions of an API to coexist so clients can upgrade on their own schedule without breaking.
Why we ask:
Needed when introducing QR and attendance endpoints without breaking the existing frontend integration.

4. Database Architecture & Scale

Database engine, topology, sizing, middleware, indexing, and failure handling.
What database technology and version are you using?
e.g., PostgreSQL 15/16, MySQL 8.0, Amazon Aurora PostgreSQL, Amazon RDS, MongoDB 6.0, DynamoDB, TimescaleDB
What is it?
The database engine determines query capabilities, indexing options, geospatial support (PostGIS for PostgreSQL), and replication features.
Why we ask:
Affects our geolocation queries (PostGIS), partitioning strategy for attendance data, and migration complexity.
Is the database single-instance, primary/replica, or Multi-AZ? What's the current DB size and monthly growth?
e.g., AWS RDS Multi-AZ, Aurora Global Database, read replicas, PostgreSQL streaming replication, Patroni HA cluster
What is it?
Multi-AZ provides automatic failover to a standby in another availability zone. Read replicas offload reporting/read queries from the primary.
Why we ask:
Current size and growth rate determine when partitioning or sharding may become necessary for 10 million identities.
Do you use database middleware like PgBouncer, Pgpool-II, or ProxySQL?
e.g., PgBouncer (connection pooling), Pgpool-II (connection pooling + read/write splitting + failover), ProxySQL, AWS RDS Proxy, HAProxy
What is it?
Database middleware sits between the application and the database to manage connection pooling, load balance reads across replicas, and provide failover.
Why we ask:
Connection pooling is critical under high concurrency — without it each request would open/close a DB connection, wasting resources.
What is your indexing strategy for Worker, QR, Attendance, and location queries?
e.g., B-tree index, GIN index, GIST index (PostGIS), partial index, composite index, BRIN index, covering index
What is it?
Indexes are database structures that speed up data retrieval. GIST indexes enable fast geospatial queries (e.g., 'find workers within 200m of worksite').
Why we ask:
Poor indexing is the most common cause of slow queries at scale. QR lookups and geofence queries need specific index types.
How do you handle database downtime or primary failure?
e.g., RDS Multi-AZ auto-failover, Aurora fault-tolerant storage, Patroni + etcd, manual DNS/connection string swap, read replica promotion
What is it?
Failover is the process of switching to a standby database when the primary fails. Multi-AZ provides automatic detection and failover typically within 1-2 minutes.
Why we ask:
Attendance transactions must not be lost during database outages. Understanding the current failover capability tells us what gaps exist.

5. SSL / TLS & Network Security

Certificate management, TLS termination, WAF/DDoS protection, and network segmentation.
How are SSL/TLS certificates managed and where does TLS termination happen?
e.g., AWS Certificate Manager (ACM), Let's Encrypt + certbot, DigiCert, GlobalSign; TLS termination at ALB, Nginx, CloudFront, or EC2 instance
What is it?
TLS (Transport Layer Security) encrypts network traffic between clients and servers. Termination is the point where encrypted traffic is decrypted — typically at a load balancer or reverse proxy.
Why we ask:
TLS termination at the load balancer offloads crypto overhead from application servers. ACM auto-renews certificates to prevent expiry outages.
Do you have a WAF (Web Application Firewall) in place?
e.g., AWS WAF, Cloudflare WAF, ModSecurity, NAXSI, F5 BIG-IP ASM, Imperva
What is it?
A WAF filters malicious HTTP/HTTPS traffic by inspecting requests against rulesets (e.g., OWASP Top 10, SQL injection, XSS).
Why we ask:
Protects APIs from common web attacks that could compromise Worker data, QR tokens, or attendance records.
Do you have DDoS protection?
e.g., AWS Shield Standard / Advanced, CloudFront + Shield, Akamai, Cloudflare, Arbor Networks
What is it?
DDoS (Distributed Denial-of-Service) attacks flood a service with traffic to make it unavailable. DDoS protection detects and mitigates these attacks at the network edge.
Why we ask:
A DDoS attack during peak attendance hours could prevent workers from marking attendance. Shield Standard comes free with AWS.
How are internal services isolated from unauthorized network access?
e.g., AWS Security Groups, NACLs, private subnets, VPC peering, Transit Gateway, Bastion hosts, AWS PrivateLink
What is it?
Network segmentation ensures that application servers, databases, and caches can only communicate with authorized services. Security groups act as stateful firewalls.
Why we ask:
If an application server is compromised, proper network isolation prevents lateral movement to the database or other services.

6. Redis, Caching & Session Management

Whether Redis or an equivalent is used for sessions, caching, and real-time state.
Are you using Redis or another caching technology?
e.g., AWS ElastiCache for Redis 7.0, self-managed Redis on EC2, Memcached, Hazelcast, Dragonfly, KeyDB
What is it?
Redis is an in-memory data store used for caching frequently accessed data, storing user sessions, rate limiting, and pub/sub messaging. It operates at microsecond latency.
Why we ask:
Caching Worker profiles, Contractor lists, and worksite data in Redis avoids repeated database queries and reduces API latency.
Where are user sessions stored?
e.g., Redis (ElastiCache), JWT (client-side, no server store), database-backed sessions (PostgreSQL), Memcached, in-memory (PM2/app server)
What is it?
Session storage determines where authenticated user state lives — server-side (Redis/DB) or client-side (JWT). Server-side sessions can be centrally invalidated.
Why we ask:
Our new services must share or integrate with the existing session/auth mechanism to avoid conflicting login states.
Are frequently accessed records (Worker profiles, Contractor lists, Worksite data) cached?
e.g., Redis with TTL, CDN caching (CloudFront), in-app memory cache (Node.js lru-cache), database query cache, ElastiCache cluster
What is it?
Caching stores copies of frequently read data in fast memory layers. TTL (Time-To-Live) controls how long data stays fresh before a refresh from the database.
Why we ask:
Without caching, every QR scan or attendance marking could trigger 3-5 database queries, quickly overwhelming the DB at scale.
What happens if Redis/cache becomes unavailable?
e.g., Fallback to database reads, ElastiCache Multi-AZ with auto-failover, Redis Sentinel, Redis Cluster, circuit breaker pattern
What is it?
Cache failure handling determines whether the application degrades gracefully (reads from DB with higher latency) or fails hard (cache is a hard dependency).
Why we ask:
We need to know whether cache availability is a requirement for attendance to function, especially during network partitions.

7. Backup, High Availability & Disaster Recovery

Backup frequency, restore testing, replication, multi-region, RPO and RTO targets.
How frequently are database backups taken? Have you done a restore test?
e.g., AWS RDS automated snapshots (5-min to hourly), pg_dump, pgBackRest, WAL-G, AWS Backup, S3 cross-region copy
What is it?
Regular backups create point-in-time copies of the database. A restore test validates that backups actually work — many teams discover corrupt backups only during a real incident.
Why we ask:
Worker, QR identity, and attendance data must be recoverable. An untested backup is not a backup.
Do you have database replication or a standby system for high availability?
e.g., RDS Multi-AZ synchronous standby, Aurora replicas, PostgreSQL streaming replication (async/sync), Patroni + etcd, Bucardo
What is it?
Replication maintains one or more copies of the database in real time. Synchronous replication ensures zero data loss during failover. Asynchronous may lose a few seconds of data.
Why we ask:
Multi-AZ alone may not protect against region-wide failures. Understanding the replication topology informs our DR strategy.
Do you have a secondary AWS region or disaster recovery site?
e.g., Multi-region architecture (ap-south-1 + ap-southeast-1), Aurora Global Database, S3 cross-region replication, Route 53 failover routing, CloudFront origin failover
What is it?
A secondary region provides geographic redundancy. If an entire AWS region goes down (rare but possible), traffic can be failed over to the secondary.
Why we ask:
For 1 crore workers, a region-wide outage in ap-south-1 could halt all attendance across India. A cross-region DR strategy may be warranted.
What are your current RPO and RTO targets?
e.g., RPO = acceptable data loss window (e.g., 5 min, 1 hour). RTO = target recovery time (e.g., 15 min, 4 hours). Measured via DR drills.
What is it?
RPO (Recovery Point Objective) is the maximum acceptable data loss measured in time. RTO (Recovery Time Objective) is the target time to restore service after a failure.
Why we ask:
These numbers define the architecture requirements — lower RPO/RTO needs synchronous replication, automated failover, and warm/hot standby infrastructure.

Can you walk through the existing user journeys — Worker, Contractor, Employer roles and their screens?

We need to understand the existing user flows, screens, and workflows to identify where QR scanning, identity binding, and attendance marking fits naturally.

Where should Employer, Contractor, and Worker master data remain authoritative?

The authoritative source is the system that holds the official/canonical record for an entity. All other systems should reference or sync from it.

What unique ID should our QR identity map to for an existing Worker?

Each Worker needs a unique, stable identifier that our QR solution can cryptographically bind to without exposing the raw ID in the QR payload.

Creates continuity between the existing platform and the new QR/attendance layer. The QR itself can contain a hashed/mapped token rather than the raw database ID.
What authentication mechanism does the existing frontend use when calling backend APIs?

What is it?
The auth mechanism determines how the frontend proves its identity to the backend for each API call. JWT tokens are self-contained; sessions require a server-side store.

What are the existing frontend-to-backend integration points we can use for Worker validation?

Integration points are the specific API endpoints or service interfaces through which the existing frontend reads and writes data.

These interfaces are potential entry points for our QR, binding, geolocation, and attendance capabilities to interact with existing data.

9. Authentication, IAM & RBAC

Identity model, role-based access, MFA posture, and OAuth/OIDC adoption.
What is the current IAM model and RBAC structure?
e.g., Custom role table in PostgreSQL, AWS IAM, AWS Cognito groups, Keycloak realms, Auth0 RBAC, CASL, Casbin
What is it?
IAM (Identity and Access Management) is the framework for identities, authentication, and permissions. RBAC (Role-Based Access Control) assigns permissions to roles rather than to individual users.
Why we ask:
BSS has multiple user types (Super Admin, Employer, Primary Contractor, Secondary Contractor, Worker) with different data access scopes.
Is MFA (Multi-Factor Authentication) enabled for administrators and privileged users?
e.g., SMS OTP, TOTP (Google Authenticator, Authy), hardware security keys (YubiKey, FIDO2), biometric (fingerprint/face), email OTP
What is it?
MFA requires two or more verification factors — something you know (password), something you have (phone/security key), or something you are (biometric).
Why we ask:
Privileged accounts (Super Admin, Employer) can access all Worker and attendance data. A compromised admin account without MFA is a major security risk.
Are you using OAuth 2.0 / OIDC for centralized authentication?
e.g., AWS Cognito, Auth0, Okta, Keycloak, Azure AD, Google Identity Platform, FusionAuth
What is it?
OAuth 2.0 provides standardized authorization flows. OIDC (OpenID Connect) adds identity/authentication on top of OAuth 2.0 — it's the modern standard for single sign-on.
Why we ask:
Centralized identity via OIDC allows our new services to authenticate users without maintaining separate user stores.
How are permissions enforced between roles at the API and database level?
e.g., Middleware-based RBAC, row-level security (PostgreSQL RLS), scoped API keys, attribute-based access control (ABAC), OPA (Open Policy Agent)
What is it?
Permission enforcement ensures that a Worker cannot view another Worker's data, and a Contractor can only see their assigned workers — implemented either at the API layer or database layer.
Why we ask:
Our QR and attendance services need to respect the same permission model. PostgreSQL RLS is particularly powerful for multi-tenant data isolation.

10. Geolocation, Geofencing & Anti-Spoofing

How location is captured, verified server-side, geofenced, and protected against GPS/VPN/device spoofing.
How is geolocation captured and verified — on-device, server-side, or both?
e.g., Browser Geolocation API, Google Play Location Services, GPS/GNSS, network-based location (Wi-Fi/cell towers), IP geolocation, PostGIS spatial queries
What is it?
Client-side capture uses the device's GPS/network. Server-side verification cross-checks the coordinates against known worksite boundaries using geospatial functions.
Why we ask:
Client-only verification is trivially spoofable. Server-side verification with PostGIS provides an authoritative check that cannot be bypassed by the user.
How is the worksite geofence defined and what radius is permitted?
e.g., PostGIS ST_DWithin (radius), ST_Contains (polygon), GeoJSON polygon fencing, circular geofence (point + radius), multi-point worksite boundary
What is it?
A geofence is a virtual boundary around a physical worksite. Workers must be within this boundary when marking attendance. Can be a simple circle or a complex polygon.
Why we ask:
The geofence precision directly impacts attendance integrity. A 500m radius is easy to spoof from a nearby location; a tight polygon with 50m tolerance is harder.
Do you have any anti-spoofing measures — mock location, rooted device, VPN/proxy detection?
e.g., Android SafetyNet/Play Integrity, iOS DeviceCheck, mock location detection (isMockLocation flag), root/jailbreak detection, IP reputation databases (MaxMind, IP2Location)
What is it?
Mock location lets users fake GPS coordinates. Rooted/jailbroken devices can bypass app-level security. VPNs can mask true IP location. Anti-spoofing layers detect these signals.
Why we ask:
Without these checks, a worker could mark attendance from home using a fake GPS app while appearing to be at the worksite.
Do you have a location-attestation mechanism that proves the device was at the claimed location?
e.g., Google Geospatial API, server-signed location tokens, timestamped + HMAC-signed coordinates, EXIF GPS metadata on a photo, Bluetooth beacon (BLE) proximity
What is it?
Location attestation provides cryptographic proof that a device was at specific coordinates at a specific time — harder to forge than raw GPS coordinates alone.
Why we ask:
For high-stakes attendance (e.g., government compliance), raw GPS is insufficient. Attestation adds a trust layer that auditors can verify.
Can attendance be recorded offline in weak-connectivity areas and synced later?
e.g., IndexedDB, SQLite (offline), Service Worker background sync, Workbox, PouchDB + CouchDB sync, AWS AppSync offline, queue-on-device pattern
What is it?
Offline attendance allows workers to mark attendance without internet, queuing the event locally and syncing when connectivity returns (with the original timestamp preserved).
Why we ask:
Many construction/agricultural worksites have poor or no connectivity. Offline support is often a hard requirement for real-world adoption.

Logs, metrics, tracing, and alerting coverage across the stack.
What is your current observability stack?

What is it?
Observability combines logs (what happened), metrics (how much/how fast), and traces (where time was spent across services). An observability stack is the set of tools that collect and visualize this data.
Why we ask:
QR scan failures, GPS errors, and attendance latency issues must be visible in real time rather than discovered through user complaints.
Do you monitor infrastructure metrics and database performance?
e.g., CloudWatch metrics (CPU, memory, disk, network), RDS Performance Insights, pg_stat_statements, slow-query log, replication lag monitoring, disk IOPS
What is it?
Infrastructure metrics track resource utilization (CPU/RAM) while database performance monitoring tracks query execution time, connection counts, and replication health.
Why we ask:
The first sign of scaling trouble is usually visible in these metrics — e.g., CPU saturation or slow queries degrading attendance API response times.
Do you have API latency (p50/p95/p99) and error-rate monitoring with alerting?
e.g., ALB access logs, CloudWatch metrics on 5xx errors, p95/p99 latency alarms, Grafana SLO dashboards, custom middleware metrics, RED metrics (Rate/Errors/Duration)
What is it?
API latency percentiles show the worst-case response times — p99 at 2 seconds means 1% of users wait 2+ seconds. Error-rate monitoring catches spikes in failures.
Why we ask:
Attendance APIs are time-sensitive. If p99 latency exceeds 3 seconds during peak hours, workers may leave before receiving confirmation.
Do you have QR scan and attendance success/failure metrics tracked as business KPIs?
e.g., CloudWatch custom metrics, Grafana business dashboards, attendance events streamed to analytics, Prometheus counters, daily success-rate reports
What is it?
Business KPI monitoring tracks business-level outcomes — how many workers successfully marked attendance, QR scan failure reasons, geofence rejection rates — not just technical metrics.
Why we ask:
Technical monitoring alone (CPU/RAM) won't tell you that 15% of QR scans failed due to poor GPS. Business KPIs surface the actual user experience.

12. Scale & Performance Baseline

Current throughput, concurrency, and tested capacity — the numbers that drive scaling decisions.
What is the current maximum number of registered workers and peak concurrent users?
e.g., Measured via DB count queries, ALB active connection metrics, session count, ConcurrentUsers in CloudWatch, RDS DatabaseConnections
What is it?
Registered workers is the total count in the database. Concurrent users is the number actively using the system at the same time (typically during 8-10 AM attendance window).
Why we ask:
Scaling from current numbers to 1 crore (10M) workers requires understanding the baseline — a 10x or 100x increase drives different architecture decisions.
What is the current peak API RPS and attendance transactions per second?
e.g., ALB RequestCount metric, CloudWatch API Gateway metrics, application-level counter, RDS DatabaseConnections, TPS from Performance Insights
What is it?
RPS (Requests Per Second) measures API throughput. TPS (Transactions Per Second) measures database write throughput during attendance marking.
Why we ask:
These numbers determine whether we need async processing queues or if synchronous processing is sufficient. Above ~500 RPS, queuing may become necessary.
Have you performed formal load testing? What was the maximum tested capacity?
e.g., JMeter, k6, Locust, Artillery, Gatling, AWS Distributed Load Testing, vegeta, wrk2
What is it?
Load testing simulates realistic traffic against the system to find its breaking point, identify bottlenecks, and validate that the system meets its throughput targets.
Why we ask:
Without load testing, the true capacity ceiling is unknown. A 1-crore worker target should be validated through testing before designing the architecture.
What was the first bottleneck encountered under load — database, application CPU, or network?
e.g., Database connection pool exhaustion, CPU saturation, memory pressure (OOM), network bandwidth limits, connection limits (ulimit, nginx worker_connections), disk I/O throttle
What is it?
The first bottleneck is the resource that saturates first under load. Understanding it tells us the primary scaling constraint — is it CPU-bound, I/O-bound, or connection-bound?
Why we ask:
If the database is the bottleneck, our solution should focus on caching, read replicas, and connection pooling. If application CPU is the bottleneck, horizontal scaling is the answer.

13. Event-Driven Architecture & High-Volume Attendance

Whether attendance is synchronous or queued, how bursts are handled, and deduplication strategy.
Are attendance events processed synchronously or asynchronously?
e.g., Synchronous (blocking API → DB insert → response), async (API → queue → worker → DB → notification), webhook callback, long polling
What is it?
Synchronous processing sends the API response only after the database write completes. Async processing accepts the event immediately, queues it, and processes in the background.
Why we ask:
Sync is simpler but blocks API threads. Async decouples ingestion from processing, allowing the system to absorb bursts without degrading response times.
Do you use a message queue or event-streaming platform?
e.g., AWS SQS (Standard/FIFO), RabbitMQ, Apache Kafka, Redis Streams, AWS SNS + SQS, AWS EventBridge, NATS, ActiveMQ
What is it?
A message queue buffers events between producers (attendance API) and consumers (workers that write to the database). FIFO queues guarantee ordering. Standard queues maximize throughput.
Why we ask:
A queue absorbs bursts of QR scans at shift start/end times (e.g., 1,000 workers scanning within 5 minutes) and smoothes the load on the database.
How do you handle sudden bursts of QR scans — is there buffering or do requests fail?
e.g., SQS buffering, Redis Streams backpressure, API Gateway throttling with retry, exponential backoff, bulk write optimization
What is it?
A burst is a sudden spike in traffic (e.g., all workers at a large construction site scanning at 9 AM). Buffering queues the excess and processes at a steady rate instead of overwhelming the system.
Why we ask:
Without burst handling, peak-time scans will result in 5xx errors or timeouts, leading to missed attendance records and frustrated workers.
If the database is temporarily slow, can incoming attendance events be buffered and replayed?
e.g., SQS dead-letter queue (DLQ), Redis Streams replay, Kafka consumer offset reset, outbox pattern, idempotent consumer, retry with exponential backoff
What is it?
Buffering decouples event acceptance from event processing. If the database slows down, events queue up instead of failing. When the database recovers, the queue drains.
Why we ask:
Database slowdowns happen during peak hours or maintenance. Without buffering, those attendance events are permanently lost.
How do you prevent duplicate attendance events?
e.g., Idempotency key (worker_id + date), UNIQUE constraint, Redis SETNX, database UPSERT, event deduplication by message ID, FIFO SQS deduplication
What is it?
Idempotency ensures that processing the same event multiple times produces the same result as processing it once. This is critical when networks cause retries.
Why we ask:
A worker who scans twice due to a network retry should not be marked as attending twice. Database UNIQUE constraints are the simplest and most reliable safeguard.

14. How the Findings Lead to Our Architecture Proposal

Do not propose technology first. Use the answers to establish: current capacity → current bottleneck → future workload → required architecture. For example, if the existing application is single-server, the first issue may be high availability and horizontal scaling. If the database is the bottleneck, database optimization/replication/partitioning may come first. If location integrity is weak, the priority may be device and location attestation.

Proposal principle: Retain what already works. Introduce new components only where the assessment demonstrates a requirement for horizontal scaling, high availability, stronger security, geospatial integrity, event processing, observability or disaster recovery. Kubernetes, Kafka, sharding and similar advanced technologies should be evaluated against measured workload and operational complexity rather than added automatically.
