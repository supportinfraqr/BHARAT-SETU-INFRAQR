Architecture Migration Ledger

Technical Rationale Document

System Architecture documentation details explaining why we shifted from Microsoft ASP.NET to containerized Python/Django and React SPA environments.

Frontend: React CSR vs Server HTML

A transition from server-side template generation (ASP.NET Razor Views) to Client-Side Rendered (CSR) React components.

Virtual DOM & Reconciliation

  • Targeted Component Edits: React's reconciliation engine tracks layout shifts in a Virtual DOM, applying minimal patches instead of reloading page documents.

Content Delivery (CDN) Offloading

  • CDN Edge Caching: vite compiles the React SPA into lightweight static HTML/JS bundles. These reside on edge CDNs (like Cloudflare) close to users.

Why we did it (Simple Terms)

To stop full-page browser refreshes and cut down response lag. By shifting UI rendering to the client's browser and distributing static code files globally on CDNs, the interface reacts instantly. This shields our server databases from handling page-delivery requests during peak shifts.

Backend: DRF API vs ASP.NET API

Migrating from .NET Framework 4.6.1 Web API 2 with stateful settings to Python 3 with stateless Django REST Framework (DRF).

Stateless API & Token Auth

  • Stateless JWT Bearer Auth: Replaced local IIS server sessions with JWT tokens. Each API container validates cryptographic token signatures without looking up databases.

Platform Independence & Costs

  • Linux/Open-Source Compatibility: Retiring SQL Server and .NET Framework removes IIS server licensing and Microsoft software costs.

Why we did it (Simple Terms)

To eliminate licensing fees and enable horizontal scaling. Stateless JWT authentication allows us to spin up as many backend server replicas as we need behind a load balancer without users logging out. Transitioning to Django and PostgreSQL lets us host everything on cheap, open-source Linux servers.

Database Scaling & Pgpool-II

Architectural enhancements to manage large transactional volumes and high-concurrency worker scan spikes.

Pgpool-II Connection Pooling

  • Connection Reuse: Pgpool-II pre-allocates database connections and distributes read queries across replication databases while writing strictly to the master node.

Redis Caching Layer

  • Low Latency In-Memory Cache: Frequently accessed database tables (like menus, user roles, permission states) are stored in Redis RAM cache.

Why we did it (Simple Terms)

To prevent the database from getting overloaded and crashing when workers check in. When hundreds of workers scan their QR codes at shift change, Pgpool-II recycles active database connections instead of opening new ones, while Redis serves static stats and layouts instantly from memory.

Hosting, DevOps & Deployments

Standardizing environments and scaling deployments smoothly via containerized setups.

Docker Containerization

  • Isolated Environments: Package Django application setups, libraries, and runtime dependencies into light Docker container images.

Nginx Proxy Routing

  • Single Port Server: Nginx routes API routes (`/api/*`) to Django while directly serving compiled static React SPA bundles on port 80/443.

Why we did it (Simple Terms)

To eliminate manual server setups and automate system deployment. Docker guarantees that the exact same environment runs on our local development PCs, staging sites, and production. It packages our services into lightweight containers that can auto-scale instantly in Kubernetes.

Ported Legacy Routes & Implementation Stubs

To retain backwards compatibility with older client mobile applications in transition, the Django backend implements 167 legacy endpoints (matching the ASP.NET DataTable schema format), while deliberately leaving non-critical integration routes as empty log placeholders.

Compatibility Mapping

  • Route Porting: Implements historical DataTable formats returning raw column-value list structures, enabling older client software versions to fetch data cleanly.
  • Security Isolation: Isolates legacy database operations from new QR validation routes, ensuring older entry points can be deprecated step-by-step.

Integration Stubs & Mock Logs

  • Mail & Communication Stubs: Email triggers write locally to `emaillog` instead of calling external SMTP servers, preventing database task blocks.
  • Payment Integration: Order creation endpoints are mock logged to local registers, removing external payment gateway dependencies during staging tests.
  • OCR Document Parsing: Accepting `raw_text` inputs as text substitutes to test workflows without needing continuous OCR server calls.

Why we did it (Simple Terms)

To ensure old mobile apps keep working without breaking while we migrate, leaving retired or non-essential features as safe placeholders. By retaining legacy paths returning the exact data structures the old apps expect, we prevent them from crashing. Using simple log files for retired features (like payment and email gateways) keeps the backend light, secure, and easy to run locally without external service subscriptions.
